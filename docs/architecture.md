# Architecture

UZEX21 answers questions about one frozen, fictional registry. It does not fetch live market prices or use model memory as a source of exchange facts.

## Data path

The importer reads the nine CSV files directly from the provided archive. Dates become typed dates, identifiers remain strings, and amounts use fixed-point decimals. Original source filenames and CSV row numbers are retained. Percent signs and spaced thousands are parsed explicitly. Import happens in a temporary database and replaces the active file only after validation.

The `registry` view contains exactly one row per deal. Contract, seller, buyer, broker and daily exchange-rate references are joined once in this view. Separate contract, company, broker and rate tables support questions without deals. The `broker_deals` view has one row per deal and broker, so rankings count a deal once for each broker on either side without a join. Import rejects duplicate keys, missing references, invalid amounts and impossible delivered quantities.

Sellers fill in contract cards, so one product appears under several spellings. At import, `product_family` merges spellings using the controlled glossary, ignoring case, punctuation and word order the glossary knows: 229 spellings become 136 products. Grades, classes and spot/forward stay separate. Rankings and breakdowns by product use this field. `volume` is quantity in lots multiplied by lot size. `amount_uzs` converts USD using the supplied rate on the deal date. `mass_kg` and `mass_t` normalize kilograms and tonnes; they remain null for other units. `unit_price` is amount divided by volume for one deal. Blank delivery fields stay null. Payment deadlines use calendar days from the deal; delivery deadlines use calendar days from payment.

## Model harness

The Responses API receives the schema, dataset coverage, business definitions and up to four previous conversation turns. The first tool call is forced to review_request. Its strict schema describes the task, reference, period, ranking metric and missing details. Application checks reject invented entity references and require necessary product, period or ranking details before querying. A price uses the data's own unit, so the unit is never a required question. A question is asked once: an optional detail the user was already asked about, or answers with `farqi yo‘q`, takes its default, and a required one ends with a request to rewrite the question instead of repeating it. Regions are recognised in Uzbek, Uzbek Cyrillic and inflected Russian forms. Only Toshkent has both a city and a region, and a reply such as `shahar` settles it. A bare six-digit number that is both a deal and a contract asks which one; 6,547 numbers are both. A number of impossible length beside a record word, such as `1000001 firma`, is explained without the model, and a real record one digit away is offered. `qanday variantlar bor?` lists the replies accepted for the open question. A named product or a year in the question is never asked for again, and rankings and lists never ask for one specific record. Company and broker names are matched on their distinctive words, ignoring legal forms such as MChJ, so a real misspelling ranks first and an unknown name has no candidates. Profit, income, paid VAT and contact questions are refused directly. Requests for examples or N arbitrary records are lists, not unidentified single-record lookups. Optional date, product and identifier filters are not required for an unfiltered list. A follow-up such as `farqi yoq` authorizes any records from the pending request’s subject and explicit filters. Strict tools then perform entity lookup, targeted clarification, restricted queries, decimal ratios and finalization. The model has no shell, browser, arbitrary Python or database-write tool.

Names are resolved against actual source strings. Unicode normalization, Cyrillic transliteration and a small Uzbek product vocabulary help lookup; fuzzy suggestions are never proof of identity. Different grades and classes remain distinct. Ambiguous company, broker and region lookups block data queries until resolved. Clarification choices come from verified lookup rows. The model must not silently select among similar identities.

SQL is parsed as an AST. One SELECT from one approved relation is allowed. Writes, external sources, schema-qualified tables, extensions, joins, CTEs, window functions, invented output constants and unapproved functions are rejected. Three narrow forms are allowed because real questions need them: HAVING on an aggregate, `SELECT COUNT(*) FROM (grouped SELECT)` to count groups, and `column [NOT] IN (SELECT column FROM approved table)`, as well as OFFSET with ORDER BY and LIMIT. Scope filters belong in WHERE so provenance covers the same records as the answer. Text filters must match a real value: `currency = 'USD'` is rejected with the real values, so an empty result always means real absence and never a mistyped filter. The real values of category columns are also listed in the prompt. A read-only DuckDB connection also disables external access and extension loading. Queries have an interruption timer, per-table row cap and memory limit. Registry output is capped at 100; directory limits allow complete current directories. Tool responses expose only 20 preview rows to the model, while application evidence retains the full bounded result for pagination and CSV. Mixed currency or measurement-unit aggregates are rejected unless grouped or explicitly normalized, and so is ranking deals directly by amount, price or volume across different currencies or units.

The sample_records tool validates the same restricted SELECT. A larger count returns 100 and the answer says so. Its input has source fields and optional WHERE filters, with no aggregate, grouping, DISTINCT, order or limit. The application draws real primary keys once using an internal random order, then executes a normal restricted query over those frozen identifiers. Dates, sample evidence, pagination and CSV therefore refer to the same records, rather than different random draws. The replayable query is retained in evidence. Random SQL functions remain forbidden in model-written queries. Sampling works on all approved relations and never invents rows when fewer matches exist.

Financial division uses Python Decimal with 50-digit calculation precision and explicit ROUND_HALF_UP display rounding. Model-provided numeric operands are not accepted: numerator and denominator must name columns in an executed result. Ratios, percentages, percentage changes and shares of a column total are supported. SQL division and AVG are blocked; MEDIAN is available.

The model cannot send a factual final answer as free text. It must reference an evidence ID issued by this request. Before accepting an answer, the application checks that it fits the question: a ranking has to name who ranks, and a request for a percentage has to contain one. The model gets one chance to correct a mismatch. The application renders source results through fixed Uzbek/Russian templates, including the filters applied, so the interpretation behind a number is visible. Some checks are always enforced, because the model cannot be relied on for them. The rows actually counted are compared with the question: a request to exclude cancelled deals fails if any are included, and turnover and prices exclude them by default. A measure cannot be divided by itself under another name. A price per kilogram cannot divide by tonnes, or the reverse. A request that keeps failing these checks ends in a service error, never in a wrong number. Labels come from the executed SQL expressions, not model-written column aliases. Currency, units, status, contract types, classifications and region names use deterministic locale dictionaries; company names and identifier codes stay unchanged. Product descriptions use a controlled Uzbek glossary; original product strings remain in CSV and saved evidence. This prevents the model from renaming a computed amount as a tax ID. Query validity alone does not establish that the model interpreted a question correctly; bilingual evaluation checks that separately.

Questions about the previous result use the about_previous_result tool instead of a new query. The application answers from the stored evidence in fixed words: whether it is complete, how it was obtained, its source, how cancelled deals were treated and confidence. Next page and file requests reuse the same stored rows, so a random sample stays the same sample.

Outcomes distinguish answer, no matching records, unavailable information, clarification and service failure. Empty lookups and tool errors cannot support a no-match claim. An API outage produces a service error, never a claim that the dataset has no answer.

The engine allows twelve tool rounds, bounded API calls, query timeouts, four simultaneous questions and a 75-second overall deadline including queue waiting in Telegram. It never streams unchecked factual drafts.

## Telegram and durability

One long-polling process receives private messages and callbacks. Each update is committed to SQLite before its offset advances. Update IDs are unique. Jobs in a chat execute in order; other chats can run concurrently. Results are persisted before sending and multipart progress is tracked. Restarts recover unfinished jobs. Source, CSV and pagination callbacks verify the requesting chat owns the answer. New replies have no Sources or CSV buttons. They show a brief inline source reference, record count, relevant dates, cancellation policy and calculation when applicable. Lists longer than ten rows attach their stored CSV automatically, unless text-only output was requested. Explicit CSV requests attach even small nonempty results. Empty, unavailable, clarification and error responses attach no file. A short file follow-up, such as `shularni csv qilib yubor` or `excel qilib ber`, exports the latest successful answer without rerunning the model; if the latest result is unavailable or absent it asks which result the user means. Legacy buttons in older messages remain ownership-checked. Named brokers.csv and participants.csv downloads use fixed source-field mappings, never user-supplied file paths or SQL.

Telegram has no general idempotency key for sendMessage. A crash after Telegram accepts a message but before the local sent marker is saved can cause a repeated reply. Incoming updates and normal retries are deduplicated; absolute exactly-once external delivery is not claimed.

Conversation history stores a summary of each result instead of its display text: every record ID up to 200, filters, columns, totals and the first rows. A follow-up over a long list therefore covers the whole list, not only what fitted on screen. Menu language and conversation history are separate for each chat. The menu preference does not force answer language: answers follow the current question or its explicit Uzbek/Russian language request. First-start language selection is optional. A persistent keyboard provides examples, help, language selection and conversation reset. Messages use escaped Telegram HTML for bold labels. Unresolved requests are stored separately per chat and survive restart. A short clarification reply is combined with the pending question; a new independent question replaces it. File preferences carry through clarification. Greetings and menu actions preserve pending requests. `/reset` clears conversation memory and unresolved questions; operational job records remain local. Local files containing questions and results are ignored by Git. Logs contain request identifiers, timings, outcomes and sanitized errors; credentials are never logged. CSV export neutralizes spreadsheet formula prefixes.

If preparing a reply fails internally, the user gets one honest service error and the model is not run again. The macOS LaunchAgent restarts the local process. Docker provides the same runtime for a Linux server. A local process lock prevents two instances sharing the same state directory. Health checks read the database and polling heartbeat without modifying job state.

## Defaults

Counts include all states unless asked otherwise. Turnover and average prices exclude cancelled deals unless explicitly included. An average unit price means a volume-weighted average in compatible units and currency. Answers show a source reference and cancellation treatment. The complete executed SQL, source samples and filters remain in local evidence records; result CSVs contain the selected result columns, not every underlying deal.

Year-based questions refer to available registry records in that year, and answers show actual observed dates. Entirely unavailable periods are declined. An explicitly requested complete period beyond the snapshot needs clarification. Observed deal dates are not proof that trading occurred on every day between them.

The data snapshot is 30 October 2026. Relative dates use Asia/Tashkent. Questions about current fulfilment, current prices, predictions, company phone numbers, profit or cancellation reasons beyond the encoded unpaid status cannot be established from this dataset.
